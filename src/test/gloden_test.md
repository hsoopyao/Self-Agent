# React 场景:

## V3.1.1.1_需求提出與整合 文档里的「SMS申請單號」編碼規則 是什么，另外行业里类似的命名规范怎么做的？分析对比两者的不同。
根據文檔 **《DMP_Workplace_V3.1.1.1_需求提出與整合_SA_V1.0.pdf》第 2.2 節（p.5）** 的表格定義，SMS申請單號由 **8 碼**組成，格式如下：

| 位置 | 欄位 | 長度 | 說明 |
|------|------|------|------|
| 第1碼 | 類別 | 1碼 | L：整線 / M：設備 / T：測試平台 / F：治工具 / H：人工站 |
| 第2-3碼 | 西元年末2碼 | 2碼 | 如 2026 → 26 |
| 第4-5碼 | 月份 | 2碼 | 01 ~ 12 |
| 第6-8碼 | 流水號 | 3碼 | 優先使用 001~999；超出後使用 A01~ZZZ（去掉 I、O） |

**示例**：`L2601001` = 整線需求、2026年、1月、第1號申請單。

## 二、行業類似的命名規範（來自網路調研）

以下是從多個來源歸納的常見企業編碼最佳實踐：

1. **首選純數字**：編碼最好全部使用阿拉伯數字，避免字母與數字混用，可減少 I/1、O/0 等混淆情形。（來源：cnblogs.com ERP編碼規則）
2. **避免特殊符號**：不要使用 "-"、"/" 等分隔符號，會降低錄入效率及口述不便。（來源：同上）
3. **長度力求短且統一**：8~12 碼為佳，同一類物料或單據的編碼長度應保持一致，便於發現漏輸、多輸。（來源：同上）
4. **字母固定在前幾碼**：若必須使用英文字母，建議排在編號前幾碼且位數一致，避免與數字混雜。（來源：同上）
5. **預留擴展空間（跳號）**：在分類號中預留空號以便日後插入新類別，是專業編碼體系的重要原則。（來源：同上）
6. **勿過度有意義**：不建議將太多屬性（規格、材質等）編入號碼中，後續新增時容易違反規則，導致體系崩潰。（來源：同上 + CSDN 企業文檔命名規範）

---

## 三、內部規則 vs. 行業規範 對比分析

| 對比維度 | 內部 SMS 申請單號 | 行業最佳實踐 | 差異分析 |
|----------|-------------------|--------------|----------|
| **編碼長度** | 固定 8 碼 | 建議 8~12 碼 | ✅ 符合，長度合理 |
| **純數字 vs 混用** | 類別為字母，流水號必要時用字母 | 建議純數字，避免字母與數字混用 | ⚠️ 部分衝突：流水號混用字母，存在 I/O 與 1/0 混淆風險（內部已主動去掉 I/O） |
| **字母位置** | 類別字母放在第1碼（最前） | 若用字母應固定在前幾碼 | ✅ 符合，字母在首位，規則清晰 |
| **分隔符號** | 不使用任何分隔符號 | 不建議使用特殊符號 | ✅ 符合 |
| **長度統一性** | 固定 8 碼統一到尾 | 強調同一類長度必須統一 | ✅ 符合 |
| **語義化程度** | 類別碼具備業務含義（L/M/T/F/H） | 建議「勿有意義」，避免後續擴充困難 | ⚠️ 有分歧：內部使用英文首字母具有較強業務語義，類別擴充時（如新增類別）可能面臨編碼衝突或認知不一致 |
| **擴展性（跳號）** | 流水號 001~999 → A01~ZZZ，容量大 | 建議預留空號、使用跳號 | ✅ 流水號容量充足，但類別碼若新增則僅 26 個字母可用（已用 5 個），未見預留機制 |

## 四、總結

內部 SMS 申請單號編碼規則在 **長度、無分隔符、字母前置** 方面與行業最佳實踐**高度一致**，是一個設計良好的精簡型編碼方案。

主要差異在於：
- 行業傾向**純數字**以徹底消除混淆，內部則在流水號中使用字母擴充；但內部已主動排除 I/O，降低了風險。
- 行業建議**弱化編碼中的業務含義**以保證長期擴展性，而內部的類別碼具有強業務語義——當前 5 個類別運行良好，但未來若大幅擴增需求類型，可能需要重新審視類別碼的容量和命名原則。

## 4.2.6 和 4.3.6 描述同一个 FR-06，差异在哪？

4.2.6 與 4.3.6 對 FR-06 數據採集的描述差異如下 [1][2]：

| 維度 | 4.2.6 需求細分流程與要點 | 4.3.6 流程詳細描述 |
|---|---|---|
| 定位 | 需求規格層面，拆解步驟與技術控制點 | 流程設計層面，給出完整業務上下文 |
| 步驟數量 | 8 個細分步驟 | 1 個步驟（設備接入） |
| 內容重點 | 技術要點（PLC/SCADA、OPC UA/MQTT/Modbus、邊緣處理、時序庫） | 業務要素（流程目的、觸發條件、前置條件、參與角色、輸入/輸出） |
| 異常/驗收 | 有明確異常場景與驗收標準（斷網告警、斷點續傳、數據完整） | 未涉及 |
| 角色 | 未顯式列出參與角色 | 明確列出：設備工程師、IT、操作工、工藝工程師 |

核心差異：
- 4.2.6 回答「要做什麼、怎麼控」：聚焦技術實現要點，如點位參數配置、邊緣清洗去重、時序庫+關係庫入庫、數據綁定工單/SN/批次，並規定斷點續傳和採集監控告警 [1]。
- 4.3.6 回答「誰在什麼條件下做」：補充業務場景，明確觸發條件（設備運行、工單開工、定時、手工補錄）、前置條件（網關、PLC/SCADA、統一時鐘）、以及四類參與角色的分工 [2]。
簡言之，4.2.6 偏向需求規格書（What & How），4.3.6 偏向流程設計書（Who & When），兩者互為補充。

## 非功能需求中的NFR-01 和 NFR-02 的指标有什么区别？

NFR-01 與 NFR-02 的指標區別如下 [1]：

| 編號 | 類別 | 需求描述 | 指標 |
|---|---|---|---|
| NFR-01 | 性能 | 看板、追溯、報表響應 | 看板 ≤ 3 秒，追溯 ≤ 3 秒 |
| NFR-02 | 可用性 | 平台穩定運行 | 99.9% |

核心區別：

- NFR-01 關注的是響應速度，即用戶操作看板、查詢追溯或打開報表時，系統必須在多長時間內給出結果（≤3 秒）。
- NFR-02 關注的是系統可用率，即平台全年穩定運行的時間比例要達到 99.9%（全年停機時間不超過約 8.76 小時）。
兩者維度完全不同：一個是"快不快"，一個是"穩不穩"。

## 4.2.10的内容是什么？

4.2.10 FR-10 異常閉環 的內容是一套從異常觸發到知識沉澱的完整處理流程，共包含 7 個細分步驟與控制點 [1][3]：
- 異常觸發：來自缺料、設備、質量、工藝、採集等方面 [1]。
- 異常分級：分為一般、嚴重、緊急三個等級 [1]。
- 上報通知：可通過自動或手工方式通知責任人 [1]。
- 響應處理：包含接單、處理、升級等動作 [1]。
- 閉環驗證：需完成原因分析、措施制定、效果驗證後才能關閉 [1]。
- 統計分析：透過帕累托圖、趨勢分析和重複異常統計來評估 [3]。
- 知識庫沉澱：將典型異常的處理方案沉澱下來以便復用 [3]。

一、业务流程

主流程：从订单到交付

1. 订单接收与评审
   - [销售/计划] 从 ERP 接收销售订单或预测（3. 製造流程總覽, p.4）

   - [DMP 系统] 自动同步订单，并进行交期风险提醒（3. 製造流程總覽, p.4）

   - [计划员] 对订单进行交期评审和优先级确认（3. 製造流程總覽, p.4）

2. 主生产计划
   - [计划员] 基于已评审订单和产能进行周/日排产与产能平衡（3. 製造流程總覽, p.4）

   - [DMP 系统] 提供排产模擬、冲突提示和版本管理支持（3. 製造流程總覽, p.4）

3. 物料需求与齐套
   - [系统] 获取工单并展开 BOM，计算净需求（4.3.3 FR-03, p.19）

   - [系统] 与 WMS 库存进行比對，做出齐套判定（4.3.3 FR-03, p.19）

   - [系统] 对缺料 WMS 库存进行排除批次，输出缺料清单并高亮影响工单（4.2.3 FR-03, p.8, p.9）

   - [系统] 通知采购、仓库、计划相关人员（4.3.3 FR-03, p.19）

4. 工单生成与下达
   - [系统/计划员] 从生产计划生成工单，绑定物料、数量、交期（4.3.4 FR-04, p.20）

   - [计划员] 根据批量、设备、交期进行工单拆分/合併（4.3.4 FR-04, p.20）

   - [系统] 在工单下达前校验工艺、物料、齐套、權限（4.3.4 FR-04, p.20）

   - [系统] 与 MES/ERP/WMS 同步工单状态（4.2.4 FR-04, p.9）

5. 生产准备与执行
   - [车间/工艺] 确认人机料法环，獲得开工许可（3. 製造流程總覽, p.4）

   - [系统] 开工前校验工艺文件版本，阻止错误版本开工（4.2.5 FR-05, p.10）

   - [操作工/设备] 执行扫码开工、報工、SN 绑定等操作（3. 製造流程總覽, p.5, 4.3.4 FR-04, p.21）

   - [系统] 自动从设备采集过程数据，并支持手工补录（3. 製造流程總覽, p.5, 4.3.6 FR-06, p.23）

   - [系统] 觸發 IQC/IPQC/FQC/OQC 检验任务（4.3.7 FR-07, p.24）

   - [质检员] 进行取样、检验并录入数据（4.3.7 FR-07, p.24）

   - [系统] 对不合格品进行自動锁定，并触发异常处理流程（4.3.7 FR-07, p.24）

8. 包装入库
   - [仓库/车间] 对完工品进行包装、貼標、入库（3. 製造流程總覽, p.5）

二、逻辑关系
模块依赖
   - 订单同步（FR-01）→ 主生产计划（FR-02）：订单是排产的直接输入来源（4.2.13 需求—流程—要點匯總索引, p.15）。

   - 主生产计划（FR-02）→ 工单管理（FR-04）：生产计划下发后会生成可执行的工单（4.3.4 FR-04, p.20）。

   - 工单管理（FR-04）→ 齐套检查（FR-03）：工单下达前必须进行物料齐套性校验（4.3.4 FR-04, p.20）。

   - 工单管理（FR-04）/工艺下发（FR-05）→ 数据采集（FR-06）：数据采集需要绑定工单、SN、工艺参数等信息（4.3.6 FR-06, p.23）。

   - 工单管理（FR-04）→ 检验管理（FR-07）：检验任务在到货、开工、完工、转序时触发，与工单状态关联（4.3.7 FR-07, p.24）。

   - 接单/工单/检验/设备 → 追溯管理（FR-09）：追溯依赖于全流程数据的完整关联，包括物料、批次、SN、工单、设备、人员、参数、检验（4.3.9 FR-09, p.25）。

   - 排产/物料/工单/设备 → 生产看板（FR-11）：看板通过抽取和计算生产相关数据，实现可视化展示（4.3.11 FR-11, p.28）。

数据流向
   - ERP → DMP：订单、物料、库存信息（6. 接口需求, p.31）。

   - PLM → DMP：BOM、工艺路线、SOP、图纸（6. 接口需求, p.31）。

   - DMP ↔ MES：通过 API/消息，双向同步工单、工艺、報工、状态（6. 接口需求, p.31）。

   - SCADA/PLC → DMP：设备状态、参数实时数据（6. 接口需求, p.31）。

   - DMP ↔ WMS：通过 API，双向同步库存、出入库信息（6. 接口需求, p.31）。

   - DMP ↔ QMS：通过 API，双向同步检验任务、结果、不良记录（6. 接口需求, p.31）。

   - DMP → BI：通過 JDBC/API，单向同步指标、报表数据（6. 接口需求, p.31）。

状态迁移
   - 订单状态：[待评审] --[通过评审]--> [已評審]（3. 製造流程總覽, p.4, 4.2.1 FR-01, p.7）

   - 工单状态：[初始] --[生成]--> [待下达] --[校验通过]--> [执行中] --[完工]--> [待关闭] --[确认]--> [已关闭]；可因异常变为 [已暂停/冻结]（4.3.4 FR-04, p.21, 4.2.4 FR-04, p.9）

   - 齐套状态：[待检查] --[系统比对]--> [齐套] / [部分齐套] / [缺料]（4.2.3 FR-03, p.8, 4.3.3 FR-03, p.19）

   - 设备状态：[运行] / [停机] / [故障] / [待机]（4.3.8 FR-08, p.25）

   - 检验状态：[待检验] --[检验判定]--> [合格] / [不合格] --[评审]--> [让步接收]；不合格品将被 [锁定]（4.3.7 FR-07, p.24）

业务规则约束
   - IF 订单同步接口失败，THEN 系统应自动重试，超限后告警（4.2.1 FR-01, p.7）。

   - IF 工单下達时版本校验错误，THEN 系统应阻止开工（4.2.5 FR-05, p.10）。

   - IF 检验判定为不合格，THEN 系统自动锁定该批次/SN（4.2.7 FR-07, p.12）。

   - IF 工单關閉时，THEN 系统必须确认数量平衡、工时、報廢、返工已确认（4.2.4 FR-04, p.9）。

   - IF 异常事件发生，THEN 系统必须根据 SLA 自动触发升级（4.3.10 FR-10, p.27）。

   - IF 库存被冻结，THEN 齐套检查时必须将其排除（4.2.3 FR-03, p.8）。

三、需求要点
   - REQ-001
       - 标题：订单同步管理
       - 描述：系统应支持从 ERP 系统通过定时（默认 15 分钟）或消息触发的方式，拉取增量订单数据（创建、变更、取消）。系统应在拉取后校验必填字段（客户、物料、数量、交期、优先级），完成主数据映射，并根据订单号 + 行号做冪等去重。处理完成后将订单写入訂單池，状态初始化为“待評審”，并通知计划员，同时对交期冲突、产能不足进行高亮提醒。
       - 验收标准：
           - 可在 5 分钟内完成订单同步。
           - 接口失败能自动重试，超限后产生告警。
           - 系统能保证订单唯一性，不会出现重复订单。
           - 交期冲突时，系统能产生可视化提醒。
       - 来源：4.2.1 FR-01, p.7
       - 关联：REQ-002, REQ-004

   - REQ-002
     - 标题：生产排产与产能平衡 
     - 描述：系统应基于已评审订单与有限产能（考虑瓶颈工序、班次、设备可利用率），支持周/日排产与产能平衡。系统应能进行排产模拟，并对交期冲突、物料短缺、设备占用冲突进行提示，支持排产结果的版本管理和滚动重排。 
     - 验收标准： 
       - 排产结果可下發为工单。 
       - 冲突能被系统识别并提示。 
       - 排产版本可追溯。 
       - 计划达成率可被统计。 
     - 来源：4.2.2 排產管理, p.8; 4.2.13 匯總索引, p.15; 4.3.2 FR-02, p.19 
     - 关联：REQ-001, REQ-004

   - REQ-003 
     - 标题：物料齐套检查 
     - 描述：系统应在工单下达前，根据工单綁定版本的 BOM 展开物料需求，考虑损耗率、替代料、安全库存，计算净需求。系统应比對 WMS 的可用库存（排除冻结库存），按齐套、部分齐套、缺料三种状态给出判定。系统应输出缺料清单，关联采购在途与预计到货计划，并通知相关部门。工单释放前，系统应执行二次校验，若不齐套则应拦截或触发审批放行流程。 
     - 验收标准： 
       - 缺料准确率 ≥ 99%。 
       - 齐套检查结果可追溯。 
       - 不齐套工单能被系统自动拦截或强制执行审批放行。 
       - BOM 错误、库存差异等异常时系统能告警。 
     - 来源：4.2.3 FR-03, p.8-9; 4.3.3 FR-03, p.19-20 
     - 关联：REQ-004

   - REQ-004 
     - 标题：工单全生命周期管理 
     - 描述：系统应实现工单从生成、拆分/合併、下達、执行（开工、報工、暫停、恢復、完工）、冻结/取消到關閉的全流程管理。工单下達前须校验工艺、物料、权限、齐套。所有工单操作（暂停/恢复/冻结/变更）应记录原因，状态和操作须与 MES/ERP/WMS 保持同步并留痕。工单關閉前必须确认数量、工时、報廢、返工已平衡。 
     - 验收标准： 
       - DMP 中的工单状态与 MES 一致。 
       - 所有对工单的操作均可追溯。 
       - 系统能强制校验工单關閉前的数量平衡。 
     - 来源：4.2.4 FR-04, p.9; 4.3.4 FR-04, p.20-21 
     - 关联：REQ-001, REQ-002, REQ-003

   - REQ-005 
     - 标题：工艺文件版本下发与管控 
     - 描述：系统应从 PLM 接收已审核生效的变更（BOM/SOP/图纸），进行版本化管理，并将其与物料、工单、工序绑定。系统应在工单下達时向 MES/工位终端下发正确版本，并要求电子签名与阅读确认。在開工前，系统必须进行版本校驗，若版本错误则应阻止开工。系统应及时回收旧版文件，并确保旧版不可继续使用。 
     - 验收标准： 
       - 能成功阻止使用错误版本的工单开工。 
       - 工艺文件变更与使用过程（谁、何时、使用何版本）可审计追溯。 
       - 旧版工艺文件被回收，無法繼續使用。 
     - 来源：4.2.5 FR-05, p.10; 4.3.5 FR-05, p.21-22 
     - 关联：REQ-004, REQ-006

   - REQ-006 
     - 标题：生产数据实时采集 
     - 描述：系统应支持接入 PLC/SCADA/传感器/网关设备，通过 OPC UA/MQTT/Modbus 协议实时采集设备状态、工艺参数、能耗数据。系统应支持配置采集点位、频率、单位、阈值。采集的数据应经过边缘处理（清洗、去重、缓存），并支持断点续传。数据最终入湖/入库，并与工单、SN、批次、设备、人员绑定。系统应监控采集延迟、丢包、断线并告警。 
     - 验收标准： 
       - 采集频率可配置。 
       - 网络中断后恢复时，系统能实现断点续传。 
       - 采集数据完整并与业务对象正确关联。 
       - 采集异常（延迟、丢包等）能产生告警。 
     - 来源：4.2.6 FR-06, p.10-11; 4.3.6 FR-06, p.22-23 
     - 关联：REQ-008, REQ-009

   - REQ-007 
     - 标题：全过程质量检验与控制 
     - 描述：系统应支持配置 IQC/IPQC/FQC/OQC 等多种检验规则、抽样标准与 AQL。系统应在对的时间点（到货、开工、完工、转序）自动触发检验任务。检验结果支持合格、不合格、让步接收三种判定，并关联 SPC 分析（控制图、CPK、趋势）。对于不合格品，系统应自动锁定，并触发 MRB（不合格品评审）等后续处理流程。 
     - 验收标准： 
       - 不合格品能被系统自动锁定并触发异常流程。 
       - 检验记录可关联到批次/SN，实现追溯。 
       - 系统能进行 SPC 分析。 
     - 来源：4.2.7 FR-07, p.11-12; 4.3.7 FR-07, p.23-24 
     - 关联：REQ-009, REQ-010

   - REQ-008
     - 标题：设备监控与维保管理 
     - 描述：系统应建立设备台账，并实时采集设备状态（运行、停机、故障、待机），计算 OEE。系统应支持点检/保養的计划、提醒、记录，以及故障报修的呼叫、派工、维修、验收全过程闭环管理。系统应能基于阈值或趋势进行故障預警，并为每台设备建立包含维修、备件、成本的完整履历。 
     - 验收标准： 
       - 设备状态采集中延迟 ≤ 5 秒。 
       - 系统能正确计算设备 OEE。 
       - 维修保养流程可闭环管理。 
     - 来源：4.2.8 FR-08, p.12; 4.3.8 FR-08, p.24-25 
     - 关联：REQ-006, REQ-010

   - REQ-009 
     - 标题：全流程正反向追溯 
     - 描述：系统应建立包含物料、批次、SN、工单、设备、人员、参数、检验的数据血缘模型。支持从原料至客户的正向追溯，以及从成品/SN 至供应商的反向追溯。系统应支持多条件查询，并能在 3 秒内返回完整链路。基于追溯结果，系统应能进行影响分析，锁定受影响范围（库存、在途、客户），并生成追溯报告。 
     - 验收标准： 
       - 在 3 秒内返回完整的追溯链路。 
       - 能导出追溯报告。 
       - 追溯权限受控。 
     - 来源：4.2.9 FR-09, p.13; 4.3.9 FR-09, p.25-26 
     - 关联：REQ-004, REQ-006, REQ-007

   - REQ-010 
     - 标题：异常事件闭环管理
     - 描述：系统应能自动或手动触发缺料、设备、质量、工艺、采集等异常事件，并进行分級（一般、严重、紧急）。系统应自动通知责任人，并跟踪處理進度。若超过 SLA 未响应，系统应自动升級。事件处理完成后，需经过原因分析、措施制定、效果验证三步骤方可閉環。系统应支持统计分析（如帕累托图、趋势图）和知识库沉淀。 
     - 验收标准： 
       - 异常闭环率可统计。 
       - 超时未处理的异常能自动升级。 
       - 重复发生的异常能被识别和分析。 
     - 来源：4.2.10 FR-10, p.13-14; 4.3.10 FR-10, p.26-27 
     - 关联：REQ-003, REQ-007, REQ-008

   - REQ-011 
     - 标题：生产管理驾驶舱与看板 
     - 描述：系统应定义计划达成率、工单状态、OEE、良率、能耗等核心指标，并支持从车间大屏、PC 端和移动端进行展示。看板应支持从工厂到工单的下钻分析，数据刷新频率 ≤ 1 分钟，看板响应时间 ≤ 3 秒。应以高亮形式展示异常信息。 
     - 验收标准： 
       - 看板页面加载/响应时间 ≤ 3 秒。 
       - 数据刷新间隔 ≤ 1 分钟。 
       - 指标异常的模块/数据能以高亮方式展示。 
     - 来源：4.2.11 FR-11, p.14; 4.3.11 FR-11, p.27-28 
     - 关联：REQ-006, REQ-008

   - REQ-012 
     - 标题：报表中心建设
     - 描述：系统应提供日报、周报、月报等固定格式报表的模板化、参数化配置功能。系统应保证报表数据口径统一、来源可查。报表支持定时或手动生成，并导出为 Excel 或 PDF。系统应具备基于角色的权限过滤和报表订阅推送功能。所有对报表的操作和版本变更应留有审计日志。 
     - 验收标准： 
       - 报表数据与源系统数据一致。 
       - 基于角色的权限过滤有效。 
       - 报表能成功导出为 Excel 和 PDF 格式。 
     - 来源：4.2.12 FR-12, p.14-15; 4.3.12 FR-12, p.28-29 
     - 关联：REQ-011
